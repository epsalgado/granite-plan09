Start here: is the Bluebeam file still a head start?

Yes. Even though the API did not see objects on the plan, the first-crack PDF is still useful. Today the specialist starts from a blank Markups List. This file fills it.

One line per draft item. Real type codes stay the Subject (H2, TP3, IL.5). NEED / CHECK where info is missing. Off-sheet lines stay off the floor. They filter, delete, add, verify, then they sign. They do not re-type 69 lines.

That is the plus. It is a head start. It is not a take-off. Say both.

Ahlsell already left this door open: sometimes the answer is in the text on the sheet, not in the geometry. The jury also asked for dead ends. “We wanted object recognition; this API cannot do it; we stopped pretending; we put the text draft where they already work” is a result.

What we hoped vs what we got

We hoped the API would read the drawing the way a specialist does: see the hook, the WC, the shelf, and count them. After testing (Wilmer’s job on PLAN 09), that is not what happened.

The API is not smart enough to pick objects off the plan. It pulled from PDF notes and other text already in the file — type marks, the hatch table, room notes. File + page only. Not a pin on the fitting.

So it is useless as “AI looked at the drawing and counted.” Do not say that.

It is not useless as a first pass of what the sheet already writes down. Specialists already read H2, TP3, IL.5 off the same notes. The App job is: put that dump in Revu, let them add / remove / sign, do not make them start from zero.

What the API can reasonably do

  • Read codes and notes on a vector PDF (H2, TP3, hatch table IL.*).
  • Return a JSON list with file + page (not an x/y on the room).
  • Give you something to stamp into Revu so checking starts from a list, not a blank page.

What it cannot do

  • Recognize drawn objects or symbols.
  • Place a box on the fitting (only on the text hit, if we searched for the code).
  • Know doors are another trade, or that a WC has no type code.
  • Map a line to an Ahlsell article number.
  • Produce a quote. A person still signs.

What to say in one breath

We used the BoM API as a text first draft. It does not recognize objects. We put that draft in Bluebeam so the specialist starts from a Markups List, not a blank page. They check, change, remove, verify, and they sign. That is the useful slice. Object take-off is the dead end we are naming.

Capability team — do we get a better API?

They are improving take-off. They are not updating the hosted API we already called (takeoff.2hero.dev).

  • App teams build on that API as a strong first draft. We do not build the engine.
  • Capability teams use it as a reference to beat. They are judged on their own reading of the drawings.
  • Polling the same job again, or sending PLAN 09 a second time, will not get a smarter list (same files come back free and unchanged).
  • If Capability produce a better list, we can import that into the same Revu loop. That is a hand-off from them, not a new version of the shared API.
